# Credential rotation and git history purge — CPUT Housing Portal

While hardening CPUT Housing Portal, I treated an earlier mistake as an active incident: a real database password and JWT signing secret had been committed in git history. Even after the working tree was cleaned, those values remained reachable in old commits, so anyone with clone access (or a mirror of the repo) could still recover them. For a Node/Express app talking to PostgreSQL and issuing JWTs, that meant both data-store access and the ability to forge session tokens until the secrets were rotated and the history was purged.

I generated new high-entropy credentials — a 64-character database password and an 86-character JWT secret — and stored them only in a local mode-600 secrets file outside the repository, never in git. I documented the safe pattern in the repo itself: PR #9 hardened `.env.example` and the README with obvious placeholders and rotation guidance (no live secrets), and that work landed on `main` as squash commit `7e0741a`. Operators are expected to copy placeholders into an untracked `.env`, apply the new values locally, and update the PostgreSQL role password to match before restarting the app.

Purging history required a full rewrite, not just deleting `.env` from `HEAD`. I used `git filter-repo` on a fresh clone to replace the old credential strings across every revision, verified with history-wide searches that the old values no longer appeared, then force-pushed cleaned `main`. The rewritten tip is `6a2b480`. Anyone who had cloned before the rewrite must delete their local copy and re-clone; otherwise they keep the old objects and may accidentally reintroduce them. Remote topic branches and GitHub’s retained objects around closed PRs can still hold pre-rewrite commits until they are removed or support-purged, so rotation remains the real control even after the rewrite.

What I take from this: never commit `.env` or any production secret; keep examples as placeholders only; assume anything that ever hit git is burned and rotate it; rewrite history when secrets leaked into commits, then force collaborators onto the new tip; and treat documentation of rotation and ignore rules as part of the fix, not an afterthought. The combination of placeholder hardening, credential rotation outside git, and a verified history purge is the remediation pattern I would apply again on a similar finding.
